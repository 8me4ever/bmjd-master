# 给朋友：岗位JD编写工作说明

你的任务是把基线 **BMJD-ALL-20261029** 的8,932个岗位JD草稿编写或专业复核为统一稿。全部岗位都要有最终处理状态；重点改进3,288个JD含推定的岗位，其余5,644岗也需覆盖。现有14份较早编写JD可以复用，但同样记录复核结果。

## 从哪里开始

先读[共同分工](00_当前进度与分工交接.md)，再读[JD编写输入](JD编写输入.json)。文件有functions和jobs两个数组：functions给职能范围和边界；jobs给当前岗位、职责系列、层级、行业及现有JD。按同一职责系列的现有上下级一起理解层级差异，再逐岗产出。不要改其job_id和任何baseline字段。

原文在[JD原文证据](JD原文证据.json)：先按source_id找sources，再按jd_sha256找texts。每岗有多个行业来源时，都应看其职责差异。当前JD是参考草稿，不是比原文更高的证据。旧标题可能错误；名称和正文冲突时记录identity_issue，由Codex改主库。

对灯光两岗，优先使用输入中的role_scoped_evidence指定条款，不得因为看到了完整父原文，又给舞台灯光增加CG渲染或给CG渲染增加舞台施工。

## 写作格式

沿用原BMJD的职责编号格式，不增设未经约定的资格、学历、汇报线或岗位价值评估段落：

```text
1、行动＋主要工作对象＋必要的结果或目的。
2、第二项独立职责。
3、第三项独立职责。
```

条款一般4—8条即可，随实际职责调整，不为凑条数编工作。避免只写“完成相关任务、整理相关资料”等没有专业对象的空话；也不要逐字拼贴全部行业差异。共性进入主JD，必要行业特例放industry_notes。

管理岗写计划、组织、协调、检查等职责；专业岗保留独立分析、设计、操作或交付的专业强度；辅助岗按实际支持边界编写。层级数字是本库约定，不直接等同某公司的职级或审批额度，不能擅自新增预算权、签字权或招聘权限。遇到现有层级与职责实质冲突，用identity_issue反馈。

## 每条职责如何说明依据

| basis_type | 何时使用 | source_refs及basis_note |
|---|---|---|
| 原文提炼 | 条款核心内容由本岗真实原文支持 | source_refs填写source_id与原文摘句quote；只引用该岗及授权条款范围 |
| 专业补写 | 用专业知识把缺失内容补成合理职责 | 不伪造来源；basis_note说明补写内容和适用假设，仍需保留内容补充标记 |
| 规则推定 | 依据职责族、相邻层级或通用规则推断 | 写清推断依据；不冒充本岗原文，也不借邻岗来源假装直接证明 |

一条混合了原文和新假设时，拆开条款或按补写/推定标注，并说明原文部分。不能因为“专业人士写过”就自动清除原有证据缺口。

## 如何交付

复制[回传模板](JD回传模板.json)，按[字段格式](JD回传格式.schema.json)填写。模板中CT205只有真实锚点，条款为空，不能算成稿。实际提交可包含多岗；最终必须覆盖8,932个基线job_id且同一提交中不重复。

每岗保留job_id、baseline_code、baseline_identity_sha256、baseline_jd_sha256，填写writing_status、clauses、industry_notes、identity_issue和必要的author_note。每条clauses包含number、text、basis_type、source_refs、basis_note。只交一段Word或聊天文字会增加回填成本，JSON是首选；需要阅读版可同时交Markdown。

- **已提交**：新稿已写完，clauses逐条编号且正文非空，依据已标注。
- **无需修改-已复核**：现稿可保留，也要回传完整条款及依据，不能只写“沿用”。
- **需澄清**：存在实质职责冲突，明确写identity_issue。已能确定的条款可以提交，不把有疑点的稿子标为已完成。
- 未开始／编写中：仅用于跟踪，不计完成。

示例条款结构如下（仅说明字段，正文必须依据实际岗位编写）：

```json
{
  "number": 1,
  "text": "填写一项完整职责。",
  "basis_type": "原文提炼",
  "source_refs": [{"source_id": "填写本岗位真实来源ID", "quote": "填写真实原文摘句"}],
  "basis_note": "说明如何合并或规范原文"
}
```

## 与Codex协作

不要在朋友工作稿里改分类、岗位代码或层级；把建议放identity_issue。Codex会单独处理主库并维护ID映射。收到改名、拆分或归并反馈时，只核对相关稿件，保留原稿与版本。代码变化不影响用基线ID定位，不能按名称或Excel行号自行配回。

完成验收：全体基线岗位去向清楚；每个保留身份一份JD；编号连续、职责对象明确、层级一致；未支持的专业补写有标记；灯光授权边界不串岗；暂缓来源不恢复；未擅改主库身份字段。
